# Changelog

## 0.11.0

Protocol revision 14: circle-scoped records (amendment A2, adopted). Author-scoped kinds, their streams and their wire bytes are unchanged.

- Add optional circle-scoped kinds and deterministic per-device/per-circle streams, reusing epochs, catch-up, cursors and delivery tracking.
- Isolate latest-wins queues and newest slots by circle; expose circle ids on history/events and index circle history. Queue limits and idempotency remain account-wide.
- Add idempotent scoped registration to the HTTP adapter, fake host and reference worker, with circle-specific publication and append checks.
- Resolve interrupted scoped publications across removals without reusing epoch numbers or distributing stale wraps; clear scoped reader keys when forgetting an author.
- `SyncReport.epoch` is the author stream's step; each own scoped stream's step is in the new `scopedEpochs`. A queued record whose circle is suspended no longer keeps `syncUntilDrained` running to `maxRounds`. An idempotency key is answered before any circle-eligibility refusal, in `enqueue()` and inside the outbox transaction. The fake host keeps a scoped stream's first registration, as the worker does. Readers memoize derived scoped stream ids per certificate and circle.
- Clarify first-seal privacy, suspension/resumption, host-visible circle metadata and host/readers/senders rollout in adopted Amendment A2.
- *Migration:* a kind may declare `scope: "circle"` in the retention policy (absent is `"author"`); such a kind needs `{ circleId }` on `enqueue` and `newest`. `Directory.openScopedStream` is optional and required only for scoped kinds (`UNSUPPORTED_OPERATION` without it); the HTTP binding is `POST /circles/{circleId}/streams`. `SyncReport` gains `scopedEpochs`; scoped records' events and history entries carry `circleId`; `PROTOCOL_REVISION` is 14. Roll out the host capability first, then revision-14 readers, then scoped kinds on senders: earlier readers do not recognise scoped streams.

Package versions follow semver for the TypeScript API. The protocol revision is a wire fact, tracked in `spec/Kavach-v1.md`; a package version names the revision it implements.

## 0.10.0

Protocol revision 13, no wire change. The first product's report on 0.9.0: queued records lost without a signal, and four small asks.

- **An audience change no longer cancels queued records.** Before, any membership change, a member's new phone, the counter running out or a hygiene rotation cancelled every record still queued, dropped its payload and told nobody, so an offline backlog (a check-in, a trip's route) was lost on reconnect. Now the records are held and sealed again under an epoch whose recipients could all read them before. When someone joined meanwhile, a **catch-up epoch** to the earlier audience carries them first and is retired once they are out, so a joiner never reads a record from before it; a removal alone needs no extra epoch, and a removed member is never a recipient. New records are never sealed under a catch-up epoch. A record already sent once is retried with its exact bytes and held only if the host fences it (`EPOCH_FENCED`), so nothing is delivered twice. Records still given up (past their window, superseded, from before payloads were kept, on a retired device) are reported with `cancelled`, the retired-device path included. Specification section 10 and the revision 13 note.
- **After review:** a record whose send failed before a join, and that the host then fenced, no longer stays held: epoch preparation, the one place that decides it, retires an active epoch that cannot carry held records needing a catch-up epoch, and the sync goes on while that epoch work is pending; a fenced record counts as held work for the drain. A catch-up epoch carries only the records of the epoch it was made for. The duplicate-open guard no longer distinguishes contexts: one runtime, one handle per database.
- **A drain covers what was queued while it ran.** `syncUntilDrained` goes on while sealed records wait to be sent, unless a round could not send at all, and `report.outbox.acceptedLocalIds` lists the local ids the relay accepted.
- **Expo: one handle per database per runtime.** `openKavach` refuses a second open of a database already open in the same runtime (`MALFORMED`), so two slots or two setups on one file fail at once instead of syncing side by side.
- **`httpTransport` reads `{ error: { code, message } }`** into the error text. **`DeliveryStatus`** is exported from the package root.
- *Migration:* `t3ApplyChange`'s result has `held` in place of `cancelled`; `SyncReport.outbox` gains `acceptedLocalIds`; `EpochRow` gains `catchUpFor`; `PROTOCOL_REVISION` is 13. A host sees one more epoch publication when an author with a backlog meets a join.

## 0.9.0

Protocol revision 12, no wire change. What the first product's integration kept as its own plumbing, where it belongs in the SDK.

- **A local id for every record.** `enqueue` returns `{ localId, recordId?, duplicate }`. The local id never changes: it is the record id when the record is sealed at once, a fresh 32-byte id when sealing is deferred. The outbox row is keyed by it, so a deferred seal and a reseal update the record id in place. `queued`, `accepted`, `cancelled` and `resealed` carry `localId` and the `idempotencyKey`; `client.delivery(localId)` answers `queued` (`sealed` or not), `held`, `accepted`, `cancelled` with its reason (`superseded`, `rotation`, `expired`, `AUDIENCE_STALE`, ...) or `unknown`, from the store, for the delivery window. Accepted rows are kept without their bytes for that window instead of being deleted.
- **`enqueue` does not fail for a rotation.** Without a usable epoch (a rotation pending or due, metadata missing, an AUDIENCE_STALE fence, the host unreachable) the record is queued unsealed (new outbox status `unsealed`, `inspect().outbox.unsealed`) and sealed in order before the next send; when the device can rotate right away, `enqueue` rotates and seals before it returns, as before. `RECIPIENT_LIMIT` and `QUEUE_FULL` stay errors. An unsealed record appears in the sender's own history and slot when it is sealed.
- **Join requests are authoritative.** The owner's pending requests are stored per circle at each full sync and `joinRequests` fires whenever they change, including to `[]`; each circle in `getState()` and `circles.list()` carries `joinRequests`. Quick syncs still skip `readRequests`.
- **One drain at a time, with a correlation id.** `syncUntilDrained` shares a running drain as `sync` shares a sync, and a full request during a quick drain runs after it. `SyncReport.opId` and `DrainReport.opId` name each run; a drain keeps one across its rounds.
- **`Transport.attach(context)`**, optional: the client hands the transport a context that answers, per call, the device it speaks for and the running `opId`.
- **`@plane31/blind-relay/http`**: the reference HTTP binding, published. Routes are relative to `baseUrl`, which carries the version prefix (the reference worker's tests now use `https://host/v1`). `headers(context)` supplies the app's authentication; the transport adds `x-kavach-device`, `x-kavach-op` and, on appends, `kavach-revision`; errors name the host's `x-request-id`; a success whose body is not JSON is `NETWORK`. The example's own copy is gone.
- **Expo: `kavachSlot`**, one account's client per runtime: `use(fn)` leases a shared handle, `close()` drains the leases before closing and new uses open afresh after it, `releaseIdle()` closes an idle handle, `erase()` marks, closes and erases. `eraseKavach` replaces an erase marker (`eraseGeneration` in the secret store, kept across erasures) before deleting anything, so another runtime's slot lets its handle go at its next use. `accountSecretStore` is exported.
- **After review:** a slot's own erasure blocks every use until it has finished, so none can reopen the old database between the close and the delete; the erase marker has two phases (`erasing` before anything is deleted, a new `erased` value after), and a slot that sees an erasure under way in another runtime lets go of its handle and opens nothing (`LOCKED`, retryable); a use rechecks its handle after reading the marker, so a close or release during the read never hands it a closed handle; a second `erase()` while one runs shares it instead of starting another. A spent counter retires the epoch again: `enqueue` reads the rotation reasons on the active epoch before deciding whether it is usable, and preparing an epoch retires an exhausted one, so records never wait unsealed behind it.
- *Migration:* `EnqueueResult.recordId` is optional, `localId` is new; the `queued`, `accepted`, `cancelled` and `resealed` events gained `localId` and `idempotencyKey`, `queued` and `cancelled` may have no record id, and `resealed` names the old id `recordId` and the new `newRecordId`; `enqueue` no longer throws `ROTATION_REQUIRED`, `COUNTER_EXHAUSTED` or `METADATA_REQUIRED`; `OutboxStatus` gains `unsealed`; outbox rows of status `accepted` stay for the delivery window; `CircleSummary` gains `joinRequests`; `SyncReport` gains `opId`. An app that kept a redirect table from record ids to its own ids can drop it.

## 0.8.0

Protocol revision 12, no wire change. A quick sync and a removal fence that holds records instead of losing them, from the first product's measurements (one phone: 620 of 1,162 requests re-asked unchanged metadata, 306 re-read streams with nothing new).

- **`sync({ mode: "quick" })`** and the same option on `syncUntilDrained`. `full` (the default) is unchanged. Quick skips `resolveAccounts`, `resolveIdentities`, `getCircle` and `readRequests`, asks the relay's new optional `syncState()` instead of `listSubscriptions()`, and reads a stream only when its head is past the scan position, the host reports `pending`, a record is unresolved, or an acknowledgement is owed (`report.inbox.skipped` counts the rest). It still publishes pending snapshots and vault updates, refreshes a stale key list and does the maintenance unless skipped. It runs full when an activation, a reset, a bootstrap or a chain is unfinished, after `AUDIENCE_STALE`, before the first full sync, and once the last full sync is older than `fullSyncEveryMs`, a new `open()` option with no default; `report.mode` and `report.promotedBecause` say which. A failed change check is reported as `listSubscriptions`, so a drain ends `incomplete`; a host without it is the new non-retryable `UNSUPPORTED_OPERATION`, with no fallback.
- **`AUDIENCE_STALE`**, a new append status: the epoch is current but addresses an account that left. The records are held, not cancelled (`report.outbox.held`, the `audienceStale` event), the epoch is retired, no new one is prepared until a full sync has learned the membership, and the next sync runs full, rotates and reseals each record once under a new id (`report.outbox.resealed`, the `resealed` event with old and new ids; the own history row, the slot and an idempotency key follow). A second refusal cancels the record with reason `AUDIENCE_STALE`. The outbox now keeps each record's payload until it is accepted or given up.
- **The client's revision travels with each append** (`appendRecord(recordId, wire, { revision })`, `PROTOCOL_REVISION` is 12), so a host answers `AUDIENCE_STALE` only to clients that read it; older clients would fail on the unknown status. The reference transport sends it as a `kavach-revision` header and maps a 404 on `GET /v1/sync-state` to `UNSUPPORTED_OPERATION`; the reference worker serves `sync-state`.
- **A circle the host says it does not have is `gone`.** A full sync whose `getCircle` succeeds with nothing stops sharing to a circle this device is a member of and rotates if the audience changed; the row stays, its members' certificates are still checked, and a signed snapshot at the same or a higher revision brings it back. A circle whose owner has an unresolved key change (a refused or not yet verifiable reset receipt) is left as it is, so only a verified receipt closes it. A failed request keeps the cached state. Before, an absent circle was ignored. A host that keeps serving the older snapshot still withholds a removal, as before; the test hosts now model withholding that way.
- **After review:** a full sync answers `AUDIENCE_STALE` and restarts the quick-sync bound only when its metadata pass resolved every circle's membership, which the pass records where the work fails or is deferred: an unpinned owner, a snapshot that fails verification, a leave the owner could not apply, an absent circle left in place because its owner's reset receipt was refused or cannot be verified yet. Until then the fence and the held records stay, and the next sync runs full again, so nothing is resealed to the old audience. A full request made while a quick sync runs gets its own full sync after it (full requests made meanwhile share it), never the quick result; a quick request shares whatever sync is running.
- *Migration:* an exhaustive switch over `ClientEvent` gains `audienceStale` and `resealed`, over `CircleStatus` gains `gone`, over `AppendStatus` gains `AUDIENCE_STALE`, over `ErrorCode` gains `UNSUPPORTED_OPERATION`. `SyncReport` gains `mode`, `promotedBecause`, `outbox.held`, `outbox.resealed` and `inbox.skipped`; `inspect().outbox` gains `held`. A transport of your own passes `options` through `appendRecord` to the host and implements `syncState` for quick syncs. Deploy the host first: it changes nothing until a client calls `syncState` or sends revision 12.

## 0.7.2

Protocol revision 11, no wire change. Hot-path reads, from a review of the code.

- **An inbound record is parsed and hashed once.** The inbox parses the wire to route it and hands the parsed document to the opener (`openParsedRecord`, internal), which verifies the signature over the parsed body under the stream's certificate key before decrypting, as before; the body hash is the parse's. Three parses and four hashes per record become one of each. `openRecordWire` is the same function over a fresh parse, so the negative vectors reject identically on both paths.
- **`getState()` is one store read** instead of six, the circles scanned once for the summaries and for `waitingFor`, and the reader-epoch check asks for one row rather than loading them all.
- **The chain follower scans one account's successions** by key prefix, not every account's.
- **No identifier in a `securityError` detail.** The refused-epoch detail named the first bytes of a stream id; it no longer does, since apps log details.

## 0.7.1

Protocol revision 11, no wire change. What an architecture review of the code turned up: four defects and four small improvements, no refactor of the client.

- **Reset receipts keep their own hash.** The persisted `resetReceipts` rows all carried the first accepted receipt's hash, so after a reload the accepted set held one hash and a re-presented older receipt was recognised only through its reset id, after the fresh-list and signer checks; under a since-rotated key it was refused as `RESET_KEY_REVOKED` instead of answered `DUPLICATE`. Every accepted receipt's hash now lives on its reset's binding (`receiptHashes`: the first and each re-attestation), and the accepted set is rebuilt from the rows, so a re-attested receipt is still a duplicate after a restart whatever happened to its signing key. Rows written before this carry one wrong hash and are read as a one-element list; the reset id still catches their receipts.
- **Succession verification follows section 4's order inside `applySuccession`.** A recorded, identical transition is `DUPLICATE` before any authentication, whatever happened to its key since (order one); anything else authenticates first, then the equivocation checks, then the transition validator. The chain follower already filtered recorded links, so only the direct path changes: an attestation of an accepted transition under a removed key is `DUPLICATE`, not `RESET_KEY_REVOKED`. A fork under a removed key is still refused as unauthenticated before it is called equivocation.
- **The reset's table list is typed.** `RESET_TABLE_POLICY` in the store says `clear` or `keep` for every table; a new table does not compile until it is listed.
- **T10 and T11 live in `transactions.ts`** (`t10PrepareReset`, `t10FinishReset`, `t11PrepareReplacement`, `t11ActivateReplacement`), with `packPendingRoots` and `unpackPendingRoots` replacing the offset slicing of the pending-roots secret. Behaviour unchanged.
- **One certificate scan per inbound record** instead of three.
- **`KavachError` carries `cause`** when it wraps a storage or primitive failure; code and stage carry nothing from it.
- **README**: the retired `Location` exports are gone from the entry-point list, the fixture note names every regeneration, and the root manifest's description no longer names a product.

## 0.7.0

Protocol revision 11: one reserved flag bit joins the header class. No existing byte changes.

- **The header class is three bits, 0 to 7.** Flag bit 3 of the record header, reserved until now, joins bits 1 and 2; classes 0 to 3 encode as before, so every existing record is the same bytes. The class keeps its meaning, an opaque per-kind value the relay may see and the product's host interprets; the protocol still names no delivery policy. Bit 0 stays reserved (no urgency flag), bits 4 to 7 too. `KindDeclaration.headerClass` accepts 0 to 7, `HeaderClass` widens, `PROTOCOL_REVISION` is 11. The fixture gains a class 5 record vector, its reserved-flag negative moves to bit 4, and `verify_vectors.py` follows. *Rollout:* a reader or host before revision 11 rejects a class above 3 as malformed. Ship the host first, then every reader, with no kind above 3; declare the new values only once the field has moved. The SDK cannot enforce the order; the README states it.
- No reader-side check of a record's class against the reader's declaration, by design: the class is the author's signed choice, the host has already acted on it, and two builds of one app may declare a kind differently during a rollout.

## 0.6.0

Protocol revision 10, no wire change. What the first device run of 0.5.0 turned up.

- **A binding that cannot be used no longer keeps the app from opening.** `openKavach({ crypto })` falls back to the portable backend when the binding's required functions are missing (its native side never installed), when one disagrees with the portable implementation, or when `ready` rejects, and reports it: `KavachSetup.cryptoBackend` is `{ kind: "native", report? }` or `{ kind: "portable", reason? }`, read from the process's active backend (so an app that installed the binding itself and opens without `crypto` sees `native`), with the per-function report when the active backend is the instance `installNativeCrypto` installed (a sodium backend set by other means carries none). `cryptoFallback: "refuse"` keeps the old behaviour (`INVALID_KEY` thrown). The self-check names a missing function apart from a disagreeing one. `installNativeCrypto` is unchanged and still throws, for apps that wire the adapters by hand.
- **`react-native-libsodium` is assignable to `crypto` without a cast.** `SodiumLike.crypto_generichash` takes its key explicitly (`null` for none), the one place the typed wrappers' declarations were stricter than the interface; the Node entry drops its own cast as the proof.
- **An undeclared record kind is `unknownKind`, not a security error.** A record that authenticated and opened but carries a kind the reader's policy does not declare is skipped and counted (`SyncReport.inbox.unknownKind`, the `receive` result `unknownKind`, the client event `unknownKind` with the author), and the cursor passes it. Retained ids are checked first, so a different body under an id the reader holds is still `EQUIVOCATION`, whatever kind it claims. It was `invalid(BAD_PAYLOAD)` with a `securityError`, which told the app the wrong thing when the author merely ran a newer version. Alarms stay reserved for records that fail authentication or equivocate; an enqueue of an undeclared kind stays `MALFORMED`. Specification section 9 and the revision 10 note. *Migration:* an app that counted on `BAD_PAYLOAD` for this case reads `inbox.unknownKind` or listens for the event; an exhaustive switch over `ClientEvent` or `ReceiveResult` gains a case.
- **`PROTOCOL_REVISION` is 10**, pinned to the specification header by a test.
- **Expo README**: which versions the backend was tested with and where (Node over the wasm wrapper; devices as the first product reported them), the react-native-libsodium 1.7.0 build failure on iOS with React Native 0.88 and its workaround, and the `onlyBuiltDependencies` entry pnpm 10 needs for the binding's postinstall.

## 0.5.0

- **A native cipher-suite backend on the phone.** `sodiumBackend(sodium)` (from `@plane31/blind-relay/adapters`) builds the libsodium backend over any object with libsodium's JavaScript API, and `openKavach({ crypto: sodium })` in the Expo package installs it from `react-native-libsodium` before the client opens (`installNativeCrypto` for apps wiring the adapters by hand). Ed25519 and X25519 then run in C instead of pure JavaScript, which is where a record's signature, a verification and an epoch's sealed boxes spend their time. Import the binding as a namespace, since its default export lacks `crypto_sign_seed_keypair`. Nothing on the wire changes; both backends pass the same vectors. The Node entry `@plane31/blind-relay/sodium` is now a thin wrapper over the same code.

- **`sync({ skipMaintenance: true })`** and the same option on `syncUntilDrained`: the retention purge, the periodic re-check of the reset-key list and the recovery-key re-save are left to a later sync; a stale list is still fetched, since verification needs it. The report says `maintenance: "done" | "skipped"`. For a short background window.

## 0.3.0

Protocol revision 9, no wire change. One release that moves generic plumbing out of products and into the SDK: a real `close()`, erasure of an account from a device, bounded multi-round sync, and account recovery as one call. The transport and host contracts are unchanged; the SDK still ships no HTTP package and no host library, and documents the transport's error contract instead.

- **Randomness at call time.** The portable crypto backend reads `crypto.getRandomValues` when bytes are needed, not when the module is imported. `@noble/hashes` captures the global at import, which on Hermes is before the app has installed a source (the Expo helper installs expo-crypto's inside `openKavach`), so every draw after enrollment failed; a circle could not be created. An app no longer needs its own shim before the SDK's import; it keeps passing `getRandomValues` to `openKavach`.
- **`close()` is a real stop.** It refuses every new operation with the new code `CLOSED`, lets the operations in flight finish their current transaction, stops a running sync at its next phase boundary, then clears the listeners so nothing is emitted afterwards. Reads still answer. It closes nothing it did not open. *Migration:* a caller that called `close()` while a sync was running got an immediate return; it now waits for the sync's current phase.
- **`eraseKavach` (Expo).** Erases one account from the device: every secret the SDK keeps for it (the list is `SECRET_NAMES` from `@plane31/blind-relay/adapters`, roots first and storage key last) and the database with its journal files, through expo-sqlite's `deleteDatabaseSync` or a `deleteDatabase` function beside a driver factory. Idempotent; an erasure interrupted halfway leaves a database that refuses to open, and running it again finishes. Nothing of another account and never the platform's synced recovery item. `openKavach` returns a `close()` that closes the client and the connection it opened; close before erasing. Expo's `SqliteStore` gains `close()`.
- **`syncUntilDrained(options)`.** Rounds of `sync` until the relay has no more records within the budget and bootstrap is complete, bounded by `maxRounds` (10) and `maxMs` (30,000). Returns the merged report plus `rounds`, `stoppedBecause` (`drained`, `maxRounds`, `maxMs`, `noProgress`, `metadata`, `authentication`, `closed`) and `remaining` (`inboxHasMore`, `bootstrapIncomplete`, `waitingFor`). Replaces the `hasMore` and bootstrap loops every app wrote.
- **`replaceDevice({ authorize, maxAttempts })`.** Account recovery over `prepareReplacement` and `completeReplacement` with the protocol's retry rules: an earlier proposal is settled through the chain first; the same proposal is kept through an unknown outcome and a refused authorization; a new proposal only after a definitive conflict, and only by the next call. The product supplies `authorize` (the host's token after its fresh sign-in, or `"reauthenticate"`). Returns `activated`, `pending`, `conflict` or `reauthenticate`; the two low-level calls remain.
- **After review of the first 0.3.0 build:** every public operation enters tracking explicitly and typed (no constructor rewrapping), and the drain and replacement helpers are tracked whole, so `close()` returns only after them; `eraseKavach` checks it can delete the database before it deletes any secret, ignores only a missing file and reports any other deletion failure as `STORAGE_FAILURE` (the secrets are gone; run it again); `syncUntilDrained` hands the time left to each round's reading budget and stops with `incomplete` and `inboxHasMore: "unknown"` when a round could not read its inbox fully, instead of calling it drained.
- **After the second review of 0.3.0:** a `close()` that lands during a round is reported as `closed` with the inbox `"unknown"`, never as drained; a contact's partly verified succession chain counts as remaining work (`remaining.chainsIncomplete`) and its pages advancing as progress, so a small budget still finishes the chain; `maxMs` is documented as the soft bound it is; a round cut short by `close()` still has its counters and errors merged into the report.
- **Transport error contract** written down in the specification (section 13): no answer, a timeout, a 5xx, 408 or 429, and a connection lost while the body streams are `NETWORK` and retryable; a body that is not JSON is a plain error; a 404 is an absent object. The reference HTTP transport's test is the conformance test.

## 0.2.0

Protocol revision 9: account recovery (amendment A1, adopted). No existing wire byte or vector changes; a revision 8 device interoperates with a revision 9 host and with revision 9 peers until a succession occurs, which a revision 8 peer sees as a bare key change.

**What this release is.** Until now a replacement phone proved it was the same account by holding the account key, recovered from the platform's synced secret store or the recovery code (identity continuity). This release adds a second way, decided per product: a phone with no secret from the old one generates fresh keys, and the host's signing authority, after the product's own fresh authentication, signs a succession that binds the account to them (account recovery). Peers verify the succession and rotate exactly as they do for a device change; circle ids, membership, ownership and pending requests are unchanged; the old phone is fenced and cannot read anything new. The price is explicit and the product's to accept: an authority that can sign successions can rebind any account, and through an owner's account inherit the owner's power over membership. The specification states that guarantee and its limits (section 15), and a product declares in its profile which models it enables; the SDK supports every model and records no product's choice.

**Upgrading from 0.1.x.** Add `replacement: "continuity" | "recovery" | "both"` to the retention policy; `open` refuses a policy without it. `continuity` keeps 0.1.x behaviour exactly. `ClientState.identityId` and `Inspection.identityId` are now the account id (constant across successions); the identity of the current key is `keyIdentityId`. Hosts implementing `Directory` gain four methods and two optional fields on `ResolvedAccount`; the reference Worker ships the migrations. A `recovery`-only profile may omit `recoveryProvider`. The review of this release ran six rounds against targeted reproductions; every finding is a regression test in `packages/core/test/review9.test.ts` and the Worker's `race.test.ts` and `streamOpen.test.ts`.

- A profile declares `replacement: "continuity" | "recovery" | "both"` in its retention policy; the SDK supports every model and records no product's choice. Peers enforce the declaration: a continuity-only deployment refuses every succession and keeps a changed key quarantined.
- `prepareReplacement()` and `completeReplacement({ successionId, authorization })` replace an account's keys on a device with no secret from the old one, under a succession the host's authority signs after the product's fresh authentication; the device then discovers its circles through the host inside `sync()`. `restoreAccount()` (identity continuity) stays and now resolves the account id through the chain.
- Accounts are named by an account id, constant across successions; `ClientState.identityId` and `Inspection.identityId` are that id, and `keyIdentityId` is the identity of the current key. `keyChanges()` reads the accepted key changes; `inspect()` reports the replacement model, a pending proposal and bootstrap progress; the sync report gains `metadata.successions` and `bootstrap`.
- Transport: `succeedAccount`, `getSuccessions`, `listCircles`, `setSharingPreference`; `ResolvedAccount` carries the chain's first page, the next generation and a certificate under the root key. The fake host and the reference Worker implement them, with a test endpoint standing in for the product's authorization. A retired device's reads are refused as well as its writes.
- The sharing preference is held at the host too, written at the join request, at circle creation and on every change, ordered by a host revision so a delayed enable never overrides a later disable.

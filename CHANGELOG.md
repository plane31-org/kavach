# Changelog

Package versions follow semver for the TypeScript API. The protocol revision is a wire fact, tracked in `spec/Kavach-v1.md`; a package version names the revision it implements.

## 0.4.0 (unreleased)

Protocol revision 9, no wire change. What the first product's integration asked for, where it belongs in the SDK.

- **`sync({ skipMaintenance: true })`** and the same option on `syncUntilDrained`: the retention purge, the periodic re-check of the reset-key list and the recovery-key re-save are left to a later sync; a stale list is still fetched, since verification needs it. The report says `maintenance: "done" | "skipped"`. For a short background window.
- **`SyncReport.timings`**: wall-clock milliseconds per phase (`resume`, `bootstrap`, `metadata`, `preferences`, `epoch`, `outbox`, `inbox`, `maintenance`, `total`) and record bytes moved (`bytesSent`, `bytesReceived`), within the safe-log rules; `syncUntilDrained` sums them across rounds.
- **`RATE_LIMITED`**, a new retryable error code with `retryAfterMs` on `KavachError`: a 429 from the host is no longer folded into `NETWORK`. The transport contract (specification section 13) and the reference HTTP transport map it, with the wait taken from `Retry-After` in seconds or as a date. *Migration:* a transport of your own should raise it for 429; an exhaustive switch over `ErrorCode` gains a case.
- **After review:** `SyncError` carries `retryAfterMs`; a send the host refused or that got no answer ends the drain with its error in the report (`outbox`, `RATE_LIMITED` or `NETWORK`) while its record stays queued; a download that fails after some pages still reports the records and bytes those pages brought (the stream summary carries the failure beside them; the transport's error is never touched); a round that was rate limited ends `syncUntilDrained` with `rateLimited` and `remaining.retryAfterMs`, so the product schedules the next attempt instead of the drain retrying at once.
- **README, "Using it well"**: the heartbeat recipe (an empty record of a silent slot kind), slot kinds for transient signals, short background windows, and a code-to-action table.

## 0.3.0

Protocol revision 9, no wire change. One release that moves generic plumbing out of products and into the SDK: a real `close()`, erasure of an account from a device, bounded multi-round sync, and account recovery as one call. The transport and host contracts are unchanged; the SDK still ships no HTTP package and no host library, and documents the transport's error contract instead.

- **Randomness at call time.** The portable crypto backend reads `crypto.getRandomValues` when bytes are needed, not when the module is imported. `@noble/hashes` captures the global at import, which on Hermes is before the app has installed a source (the Expo helper installs expo-crypto's inside `openKavach`), so every draw after enrollment failed; a circle could not be created. An app no longer needs its own shim before the SDK's import; it keeps passing `getRandomValues` to `openKavach`.
- **`close()` is a real stop.** It refuses every new operation with the new code `CLOSED`, lets the operations in flight finish their current transaction, stops a running sync at its next phase boundary, then clears the listeners so nothing is emitted afterwards. Reads still answer. It closes nothing it did not open. *Migration:* a caller that called `close()` while a sync was running got an immediate return; it now waits for the sync's current phase.
- **`eraseKavach` (Expo).** Erases one account from the device: every secret the SDK keeps for it (the list is `SECRET_NAMES` from `@plane31/blind-relay/adapters`, roots first and storage key last) and the database with its journal files, through expo-sqlite's `deleteDatabaseSync` or a `deleteDatabase` function beside a driver factory. Idempotent; an erasure interrupted halfway leaves a database that refuses to open, and running it again finishes. Nothing of another account and never the platform's synced recovery item. `openKavach` returns a `close()` that closes the client and the connection it opened; close before erasing. Expo's `SqliteStore` gains `close()`.
- **`syncUntilDrained(options)`.** Rounds of `sync` until the relay has no more records within the budget and bootstrap is complete, bounded by `maxRounds` (10) and `maxMs` (30,000). Returns the merged report plus `rounds`, `stoppedBecause` (`drained`, `maxRounds`, `maxMs`, `noProgress`, `metadata`, `authentication`, `closed`) and `remaining` (`inboxHasMore`, `bootstrapIncomplete`, `waitingFor`). Replaces the `hasMore` and bootstrap loops every app wrote.
- **`replaceDevice({ authorize, maxAttempts })`.** Account recovery over `prepareReplacement` and `completeReplacement` with the protocol's retry rules: an earlier proposal is settled through the chain first; the same proposal is kept through an unknown outcome and a refused authorization; a new proposal only after a definitive conflict, and only by the next call. The product supplies `authorize` (the host's token after its fresh sign-in, or `"reauthenticate"`). Returns `activated`, `pending`, `conflict` or `reauthenticate`; the two low-level calls remain.
- **After review of the first 0.3.0 build:** every public operation enters tracking explicitly and typed (no constructor rewrapping), and the drain and replacement helpers are tracked whole, so `close()` returns only after them; `eraseKavach` checks it can delete the database before it deletes any secret, ignores only a missing file and reports any other deletion failure as `STORAGE_FAILURE` (the secrets are gone; run it again); `syncUntilDrained` hands the time left to each round's reading budget and stops with `incomplete` and `inboxHasMore: "unknown"` when a round could not read its inbox fully, instead of calling it drained.
- **After the second review of 0.3.0:** a `close()` that lands during a round is reported as `closed` with the inbox `"unknown"`, never as drained; a contact's partly verified succession chain counts as remaining work (`remaining.chainsIncomplete`) and its pages advancing as progress, so a small budget still finishes the chain; `maxMs` is documented as the soft bound it is; a round cut short by `close()` still has its counters and errors merged into the report.
- **Transport error contract** written down in the specification (section 13): no answer, a timeout, a 5xx, 408 or 429, and a connection lost while the body streams are `NETWORK` and retryable; a body that is not JSON is a plain error; a 404 is an absent object. The reference HTTP transport's test is the conformance test.

## 0.2.0

Protocol revision 9: account recovery (amendment A1, adopted). No existing wire byte or vector changes; a revision 8 device interoperates with a revision 9 host and with revision 9 peers until a succession occurs, which a revision 8 peer sees as a bare key change.

**What this release is.** Until now a replacement phone proved it was the same account by holding the account key, recovered from the platform's synced secret store or the recovery code (identity continuity). This release adds a second way, decided per product: a phone with no secret from the old one generates fresh keys, and the host's signing authority, after the product's own fresh authentication, signs a succession that binds the account to them (account recovery). Peers verify the succession and rotate exactly as they do for a device change; circle ids, membership, ownership and pending requests are unchanged; the old phone is fenced and cannot read anything new. The price is explicit and the product's to accept: an authority that can sign successions can rebind any account, and through an owner's account inherit the owner's power over membership. The specification states that guarantee and its limits (section 15), and a product declares in its profile which models it enables; the SDK supports every model and records no product's choice.

**Upgrading from 0.1.x.** Add `replacement: "continuity" | "recovery" | "both"` to the retention policy; `open` refuses a policy without it. `continuity` keeps 0.1.x behaviour exactly. `ClientState.identityId` and `Inspection.identityId` are now the account id (constant across successions); the identity of the current key is `keyIdentityId`. Hosts implementing `Directory` gain four methods and two optional fields on `ResolvedAccount`; the reference Worker ships the migrations. A `recovery`-only profile may omit `recoveryProvider`. The review of this release ran six rounds against targeted reproductions; every finding is a regression test in `packages/core/test/review9.test.ts` and the Worker's `race.test.ts` and `streamOpen.test.ts`.

- A profile declares `replacement: "continuity" | "recovery" | "both"` in its retention policy; the SDK supports every model and records no product's choice. Peers enforce the declaration: a continuity-only deployment refuses every succession and keeps a changed key quarantined.
- `prepareReplacement()` and `completeReplacement({ successionId, authorization })` replace an account's keys on a device with no secret from the old one, under a succession the host's authority signs after the product's fresh authentication; the device then discovers its circles through the host inside `sync()`. `restoreAccount()` (identity continuity) stays and now resolves the account id through the chain.
- Accounts are named by an account id, constant across successions; `ClientState.identityId` and `Inspection.identityId` are that id, and `keyIdentityId` is the identity of the current key. `keyChanges()` reads the accepted key changes; `inspect()` reports the replacement model, a pending proposal and bootstrap progress; the sync report gains `metadata.successions` and `bootstrap`.
- Transport: `succeedAccount`, `getSuccessions`, `listCircles`, `setSharingPreference`; `ResolvedAccount` carries the chain's first page, the next generation and a certificate under the root key. The fake host and the reference Worker implement them, with a test endpoint standing in for the product's authorization. A retired device's reads are refused as well as its writes.
- The sharing preference is held at the host too, written at the join request, at circle creation and on every change, ordered by a host revision so a delayed enable never overrides a later disable.
- Error codes `SUCCESSION_BINDING`, `SUPERSEDED_IDENTITY`, `AUTHORIZATION_REQUIRED`, `AUTHORIZATION_EXPIRED`, `REPLACEMENT_CONFLICT`, `SUCCESSION_PENDING`; state `replacementPrepared`. A device retired by a succession erases its account seed and reports `SUPERSEDED_DEVICE`.
- Fixture: a type 9 vector, four negatives (26 in all) and ten verifier cases, verified by the Python checker.
- After review of the first implementation: every succession goes through one path with the policy gate first, so a first contact with a chained account pins nothing on a continuity-only deployment (and quarantines) or when the chain does not verify; a retired owner key can only vouch for a circle held at revision 0; the Worker's replacement and activation writes are conditional on winning the compare-and-swap; a bootstrap circle that fails is retried by every sync and named in the error; a paged chain resumes from its verified prefix within the sync's `catchUp` budget. `recoveryProvider` is optional on a recovery-only profile.
- After the second review: one transition validator (identity, generation, retired identities, device ids) serves `applySuccession`, first contact, restore and self-retirement, so a fresh device and an established peer agree on every chain and `A → B → A` is refused everywhere; a pinned peer reconciles the served chain with the links it already accepted, so a second and third replacement apply cleanly; a served chain is followed even under an unchanged key; the Worker opens the new device's stream as an idempotent completion step, on `ALREADY_COMMITTED` retries and before the device's first publication; a recovery-only client without a provider builds and publishes no vault, and `registerAccount` and `resetAccount` take an optional vault.
- After the third review: a cached chain prefix whose signer left the list is re-attested from the host instead of retried forever; a saved cursor is resumed even when every served link was already on record, and recorded links no longer consume the sync budget; a served link that differs from a recorded transition is authenticated before it counts as equivocation (a forgery is `BAD_SIGNATURE`); `recoveryCode()` is `NOT_AUTHORIZED` where the profile does not enable identity continuity or the client has no vault.
- After the fourth review: a replacement device verifies and keeps its account's whole earlier chain and every key in it at activation, so an owner replaced twice without a bootstrap between still verifies the circle it owns, and a phone several replacements back follows its own chain and retires; a failure to follow the own chain is reported as `ownSuccession` instead of being swallowed.
- After the fifth review: the chain traversal takes a generation bound that applies to every page, so a replacement activates against a paged history on the retried commit and on a sync resume alike; `openKavach` in the Expo package takes an optional `recoveryProvider`, forwarded only when given, with core enforcing the requirement for `continuity` and `both`.
- After the sixth review: an activation whose account resolution is not served is `METADATA_REQUIRED` with the proposal kept, instead of finishing with an empty history and losing the account's older keys; an empty history is accepted only at the account root.

## 0.1.1

First published versions of `@plane31/blind-relay` and `@plane31/blind-relay-expo`, implementing protocol revision 8. (0.1.0 was tagged but never reached the registry; its tag points at an earlier tree.)

- The SDK is product-agnostic. A product declares its record kinds in the retention policy (retention, queue mode, history, newest slot, header class) and keeps its payload codecs in its own profile; the SDK never parses a payload. One `enqueue(kind, payload, options)`, one `newest(identityId, kind)`, one `recordStored` event and one `refresh` event.
- Every record plaintext is an envelope (version, kind, event time) followed by the payload; the header shows the relay only the kind's declared class. The newest slot per author and kind orders by device generation, event time clamped to the send time, then (epoch, counter), on the reader and for the sender's own records alike.
- Durable outbox with an idempotency key answered before anything needs the network; a bounded, budgeted inbox with `hasMore`; per-stream errors in the sync report with the stream and author named; history served from a time-ordered index with stable cursors.
- Expo adapters: SecureStore secrets, SQLCipher store with a cross-process writer lock, foreground-only key provisioning, recovery providers, a trusted clock, and a Web Crypto install for Hermes.
- Conformance fixture regenerated for revision 8 and verified by the Python checker.
